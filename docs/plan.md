# 개발 계획 (1인)

> **현재 위치:** M5 진행 중. 자기 수정, 역할별 스키마·OKF 거르기, 검색 비교(키워드 채택), 지식 층 비교, 되묻기 완료. 남은 것은 보고서 대조.
>
> 작업이 끝날 때마다 이 줄과 아래 체크박스를 갱신한다.

원본 기획은 개인 드라이브의 "ERP 자연어 질의 시스템 기획안 (1인)"이다. 이 문서는 그중 개발에 필요한 부분만 옮긴 것이며, 레포에서는 이 문서가 기준이다.

**기간은 정하지 않는다.** 마일스톤 순서와 점검 기준만 지킨다. 앞 마일스톤의 점검을 통과하지 못하면 다음으로 넘어가지 않는다.

## 범위

- **1단계 (반드시):** 이것만 있어도 결과 표와 화면이 나온다.
- **2단계 (차별점):** 검색, 되묻기, RLS 비교 등.
- 3단계 기능(결과 마스킹, 오픈 모델 비교, MCP 서버, Odoo 애드온, 의미 계층, 문서 RAG, LoRA)은 **하지 않는다.** 아래 "2차 목록"에만 적는다.
- M4(1차 마감) 이후 떠오른 새 기능도 2차 목록으로 보낸다.

## M5 검색 비교

평가 50문항, 스냅숏 `erp-20261103.zip`, today 2026-11-03, 2026-11-07 측정, claude-haiku-5-5, 자기 수정 1회. 조합마다 세 번 돌린 정답 수와 평균이다. 예시는 `eval/examples/` 40개(`examples_version` `ece050acaa3e`), 검색은 역할로 거른 뒤 3개.

| 프롬프트 | 검색 없음 | 키워드 (BM25) | 임베딩 |
|---|---|---|---|
| OKF 포함 (`86a1b1127993`) | 47·45·45 (45.7) | **48·48·48 (48.0)** | 46·45·45 (45.3) |
| 프롬프트만 (`7e33530d232b`) | 40·42·41 (41.0) | 41·41·43 (41.7) | 42·44·41 (42.3) |

영역별 평균 (세 번):

| 영역 | OKF 없음 | OKF 키워드 | OKF 임베딩 | 프롬프트만 없음 | 프롬프트만 키워드 | 프롬프트만 임베딩 |
|---|---|---|---|---|---|---|
| 판매 /13 | 11.7 | 11.3 | 10.7 | 11.7 | 10.3 | 12.7 |
| 구매 /12 | 11.3 | 11.7 | 12.0 | 11.0 | 10.7 | 11.3 |
| 재고 /12 | 11.0 | 12.0 | 10.3 | 9.0 | 11.0 | 11.0 |
| 회계 /13 | 11.7 | 13.0 | 12.3 | 9.3 | 9.7 | 7.3 |

- **검색 비교**: OKF 포함에서 키워드가 +2.3문항이고 세 번 모두 48이었다. 임베딩은 검색 없음과 차이가 없다. 임베딩(paraphrase-multilingual-MiniLM-L12-v2)은 영역이 다른 예시를 자주 골랐다(stock-003 출고 질문에 회계 예시, account-009 미수금 질문에 재고·판매 예시). 그래서 기본값을 `NLQ_RETRIEVE=keyword`로 두었다([ADR 0004](adr/0004-example-retrieval-in-memory.md)).
- **지식 층 비교**: RAG만(프롬프트만 + 검색) 41.7~42.3, OKF + RAG(키워드) 48.0. 예시만으로는 OKF 묶음을 대신하지 못한다. 특히 회계는 RAG만일 때 7.3~9.7/13으로, 매출·미수금 정의와 부호 규칙은 예시 세 개로 전해지지 않는다. 프롬프트만 + 임베딩은 회계 예시를 잘못 골라 검색 없음(9.3)보다도 낮다.
- 키워드 검색이 고친 문항: stock-007(날짜를 물었는데 timestamp를 낸 문항)은 OKF 검색 없음에서 세 번 다 틀렸고 키워드에서는 세 번 다 맞았다. `::date`를 쓰는 예시가 함께 들어갔다. sales-002는 여전히 모든 조합에서 틀린다.
- 한 번만 잰 M4 결과 표(OKF 포함 46)와 이 표의 "검색 없음"(45~47)은 같은 범위다. 회차 변동이 ±1~2문항이라, 한 번 잰 차이는 그보다 커야 읽는다.

claude-haiku-5-5, 2026-11-07, OKF 포함 + 키워드 검색, 자기 수정 1회, 각 세 번. 되묻는 기준은 주문/송장 기준, 부가세 포함 여부, 송장 합계의 환불 차감 셋이다([architecture.md](architecture.md) "되묻기").

| | 되묻기 끔 | 되묻기 켬 |
|---|---|---|

| 첫 답이 고른 기준과 맞음 | 3·4·4 | — (바로 답한 1문항은 세 번 모두 맞음) |
| 기준을 넣은 뒤 정답 | 8·8·8 | 8·8·8 |
| 끝까지 가서 맞은 문항 | 3.7 | 8.0 |

- 기준이 정해진 질문에서는 되묻지 않았다(150번 중 0번). 되묻기를 켜도 50문항 점수는 변동 범위 안이다.
- 기준이 갈리는 질문에서는 되묻지 않으면 8개 중 3~4개만 사람이 원한 기준과 맞는다. 되물으면 8개 모두 맞는다.
- 안 되묻는 1문항은 clarify-004("지난달 확정 주문 금액 합계")다. 부가세 기준이 빠졌지만 모델이 부가세 포함으로 답했고, 고른 기준과 같았다.
- 되묻기 세트를 만들 때 처음 쓴 답 "환불은 빼고"가 "환불 문서 제외"와 "환불 차감"으로 갈려 한 번 틀렸다. 답을 "고객 환불을 차감"으로 고친 뒤 위 숫자를 쟀다.

## 미리 알고 있는 위험

| 위험 | 대응 |
|---|---|
| 데모 데이터 날짜가 실행일마다 바뀜 | 스냅숏, "오늘 날짜" 고정값 |
| 평가 질문이 예시에 섞여 점수가 부풀려짐 | `eval/questions/`와 `eval/examples/` 분리 |
| `set_config`, `pg_sleep` 등 위험 함수 | guard 함수 허용 목록, 우회 테스트에 포함. guard가 놓쳐도 `nlq_readonly`에 실행 권한이 없다(PUBLIC에서 회수) |
| RLS가 Odoo 동작을 깨뜨림 | `nlq_readonly`에만 정책 적용, `FORCE` 금지 |
| 채점 오판 (행 순서, 열 이름, 반올림) | 비교할 때 무시 |
| 평가를 반복할수록 API 비용이 쌓임 | 개발 중에는 Haiku, 결과 표용 측정만 Opus. 평가 전용 키에 월 한도 |
| "Odoo ORM API를 쓰면 권한이 자동 적용되지 않나"라는 반론 | SQL을 택한 이유를 ADR로 남김 |
| 하루 이상 막힘 | 범위를 줄이거나 우회로를 택하고 드라이브 troubleshooting 폴더에 기록 |
